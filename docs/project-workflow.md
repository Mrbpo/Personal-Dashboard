# Canvas Dashboard 项目协作流程

本流程适用于本仓库的代码、文档和配置改动。用户在总调度对话提出需求；具体实施在同一个 **WEb** 项目中由独立 Codex 任务完成。

| 对象 | 用途 |
| --- | --- |
| 总调度任务 | 整理需求、分配实施、检查证据并审阅 PR。任务 ID：`01a0cc53-5c1a-7d33-848e-52821d4713a1`。 |
| WEb 项目 | 容纳实施任务。项目 ID：`471602db-fb09-4ae2-bc1f-a6657c0925da`。 |
| GitHub Issue | 记录已决定实施的目标、范围与可验收结果。 |
| Codex 实施任务、工作树与分支 | 隔离一次实施和它的 Git 改动，避免互相覆盖。 |
| Pull Request（PR） | 提交改动与验证证据，关联 Issue，供 CI 和总调度审阅。 |
| Release | 按现有正式发布机制单独安排上线；合并 PR 不等于发布。 |

## 1. 需求与 Issue

总调度先判断需求是讨论、研究，还是已决定实施。纯讨论或研究可以留在总调度对话；一旦要修改代码、文档或配置，先建立 Issue，再开始具体实施。使用 Bug 或 Feature 模板即可，重点写清现状、目标和如何验收；不必让用户预先提供技术方案。总调度可根据研究结果补充范围和验收标准。

一个 Issue 应让实施任务知道什么算完成：可观察的结果、必要的边界和相关链接。如果实施中发现需求明显变化，先更新 Issue 或在其中说明决定，避免 PR 与验收目标脱节。

## 2. 独立实施

总调度为具体工作在同一个 WEb 项目中新建 Codex 任务，并交付 Issue 链接与验收目标。每个实施任务使用自己的 Git 工作树，从最新的 `origin/main` 建立独立分支（建议 `codex/<简短主题>`）。不要直接在 `main` 改动，也不要共用其他任务的工作树或分支。开始前检查工作树与远端状态；如基础分支落后，先同步并处理冲突。

实施任务在自己的分支完成改动，执行与范围相称的验证，记录命令、结果和未覆盖的部分。涉及 UI 时检查实际界面并准备截图；不涉及 UI 时在 PR 中写明“不适用”。不要把密钥、私人课程资料或敏感截图提交到仓库。

## 3. PR、检查与审阅

把分支推送到 GitHub，创建目标为 `main` 的 PR。在描述中使用 `Closes #<Issue 编号>`，填写改动摘要、验证结果、风险或限制，以及 UI 截图或“不适用”。一个 PR 应有明确、可审阅的范围；发现独立的新需求时另建 Issue。

等待 `.github/workflows/check.yml` 的 PR 检查完成，并由总调度对照 Issue 验收标准审阅。CI 失败、审阅意见或合并冲突由实施任务在原分支修复并更新证据；修复后重新等待检查。**只有 CI 与总调度审阅均通过，才可合并。**实施任务不自行合并；由总调度协调合并。合并后核对 Issue 是否由 PR 关闭，并向总调度报告结果。

## 4. 正式 Release

普通 PR、合并和推送不会自动触发正式生产发布。需要上线时，另按 [发布指南](release-guide.md) 与现有 `.github/workflows/release.yml` 处理版本、正式 Release、部署和上线检查。纯流程文档变更不因此触发正式 Release；不要为了合并 PR 改动发布工作流。

## 5. 阻碍与主动回报

实施任务在以下节点使用 `mcp__codex_app__send_message_to_thread` 主动发给总调度任务（ID 见上表），不依赖定时自动化：

- **实质阻碍：**说明卡住的步骤、已尝试的方法、需要的决定或外部条件，并附 Issue、日志或相关链接。
- **PR 就绪：**发送 PR 与 Issue 链接、改动摘要、验证结果、CI 状态、风险和 UI 截图位置；明确尚待审阅或检查的事项。
- **完成：**发送合并 PR、关闭的 Issue 和必要的 CI／发布状态链接；如工作停在未合并的 PR，明确说明当前状态，不能称为已合并或已发布。

若 CI、权限或依赖长期阻碍进展，在 Issue 或 PR 留下可复查的事实，同时立即向总调度回报。总调度决定是否调整范围、补充条件或暂停合并。
