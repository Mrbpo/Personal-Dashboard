# Development study-answer planning

Issue #133 adds only the first phase of a complete-answer pipeline. `KernelService.planStudyAnswer(owner, query, {courseId?}, policy)` performs real library retrieval and proposes answer requirements, evidence clusters and scope/conflict distinctions. It does not generate answers, execute supplemental queries, audit claims or revise citations. It is not connected to UI, application routes or production defaults.

## Input and source boundary

The fixed method is keyword search with `relatedDocuments=true`, limit14, current full evidence, section parents, and original verified images under the existing shared image budget. Semantic retrieval, embeddings, hybrid search and AI reranking are disabled in this development lane. A public title may be part of the natural query. `documentId`, `paperId`, `sourceHint` and other hidden source filters are rejected; an optional course must come from explicit user context. This is not equivalent to the old hybrid PDF retrieval benchmark.

The context callback is the extracted existing `answerStudyContent` callback. Default answering retains its options, source reads, provider request and behavior. Every planning recheck uses those same current source/evidence identities; a change fails the attempt. Parser warnings, unavailable parents and omitted-image accounting remain in the request and receipt. The supplied context is not claimed to cover the entire library.

Eligible unstructured plain text may carry the shared reader's non-persisted `flat-persisted-text-v1` provenance. Its manifest hash, `originalHierarchyVerified=false` and `originalFileCompletenessVerified=false` enter the provider input/fingerprint and the plan receipt's `flatTextContexts`. This does not certify original-file coverage or author hierarchy; registered structures keep their original behavior.

## Plan

- `requirements`: all material question aspects with `requestedScope` (subject, attribute, unit, population, stage, configuration, time). Unknown dimensions are null.
- `clusters`: requirement IDs, actual selectable q/image IDs, separate source-grounded `groundedScope`, and sufficient/needs-evidence/ambiguous status. An asserted grounded scope needs source evidence. Metadata eN/supportId are not selectable.
- `conflicts`: two different clusters, evidence on both sides, same-context/different-context/unresolved comparability and a reason. Each side must cite its own cluster evidence; a source cannot be silently substituted.
- `missing`: preserved requirement, reason, and optional lexical supplement query. Nothing executes it in this phase.

Every requirement must have a cluster or a missing entry. Shared schema definitions list real source IDs once. Structural validation is not semantic proof. A valid plan returns `ready-for-review`, `needs-evidence`, `incomplete-context` or `capacity-exceeded`. The pilot permits at most six clusters to advance; a larger plan is retained intact and reported incomplete. `semanticVerified` and `wholeAnswerVerified` remain false in all cases. A refusal or smaller plan cannot establish complete-answer accuracy.

## Paid boundary and future phases

Planning requires the existing isolated development policy, ordinary ledger with bypass explicitly false, frozen mini54 rates/context, and mandatory durable `beforeAttempt`/`recordResponse` functions. There is at most one gpt-5.4-mini low/4000/30s request per invocation, with no retry or upgrade. The actual complete request, schema, image token bound and framing must fit the existing300k input cap before reservation. The attempt exposes both the real input/usage bound and the ordinary full-body `/2` reservation bound; callers must fund their maximum and enforce a batch cap. Raw response bytes are journaled before diagnostic parsing and retained on model/schema/usage/source failure. Ambiguous timeouts retain ordinary reservations.

The six exposed query-only inputs remain ignored operational artifacts, separately frozen and subject to coordinator execution approval. Initially only six retrieval plans may be reviewed for paid execution; there is no authorization from this document. No existing answer/Gold/score is changed. Later per-cluster generation, optional bounded supplement/finalization, and physically isolated per-claim audit need separate actual-body and total-call budgets. A per-cluster cap cannot bound auditing unless the number of produced claims is also frozen. No whole-source self-audit from the closed PR130 is reused.

Plan calibration is not the final goal. Three independent complete learning-oriented material/question sets, multi-source retrieval, useful complete answers, applicable citations and source text/formula/table fidelity still require separate acceptance. Code/CI, service deployment and production switching are distinct delivery states.

## Explicit contract and local evidence phases

The contract-bound plan v2 schema and validator require at least one actual selectable source ID for every cluster and source sub-scope, including `needs-evidence` or `missing` proposals. Requirements with no evidence belong in top-level `missing` only; empty cluster/sub-scope arrays remain valid. This prevents an evidence-free asserted grounded scope, without inventing citations or relaxing current-source checks. The original unbound plan protocol and historical raw outputs remain unchanged. This uses the supported Structured Outputs array `minItems` constraint ([official documentation](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses)); structural validity does not establish answer coverage.

The original `planStudyAnswer` protocol and six recorded pilot requests/results remain unchanged. Its first calibration exposed false-ready provenance and scope/conflict omissions; a structurally valid plan is not an accepted answer. The following development entries are separate, explicit calls, not an automatic chain:

- `createStudyQuestionContract(query, policy)` sees only the original query. It freezes the complete question, ordered requirements with requested scope, request/raw hashes and a contract hash. The contract is fallible: it does not prove interpretation or completeness.
- `planStudyAnswerWithContract(owner, query, contract, {courseId?}, policy)` uses the same real keyword/related retrieval and current evidence as the original entry. The provider cannot return a replacement requirements array. It maps immutable requirement IDs to clusters and missing entries. Source-discovered parallel datasets, subjects and configurations remain `sourceSubscopes` under those IDs, with real evidence and covered/missing/ambiguous status; they neither become new user questions nor disappear because the question did not enumerate them. Optional unrequested counts are not new requirements. A covered sub-scope must cite its sufficient clusters' actual evidence.
- `verifyStudyAnswerPlanCluster(owner, query, contract, binding, clusterId, {courseId?}, policy)` restores that cluster's selected q/i units against the current Kernel context. Its provider receives only the question-derived contract, assigned requirements, candidate grounded scope, selected original text/PNG, and corresponding local evidence metadata/warnings. Other clusters, global source lists, full source bodies and their summaries are absent. Original plan/request/raw identities and the current source fingerprint/quote manifest are hashes in the local receipt, not substitute evidence. More than20 selections is rejected without truncation.

Local factual support and responsiveness are distinct findings. Several selected references can jointly establish material parts; background, partial support or an unanswered relation requires an explicit gap and cannot be locally ready. Responsiveness concerns the requested relation within the evidence-established candidate sub-scope; it does not certify all parallel scopes or the entire requirement. An explicitly requested total cannot be satisfied by a subset. Candidate grounded scope is tested, not accepted as evidence for itself. Dataset origin does not establish label provenance, captions do not establish unseen numbers, and a subset or processing stage does not establish a different population or final result. The checker returns judgments and gaps, without generating a replacement answer or additional facts. Request identity is recomputed from the actual original-plan builder; a raw hash binds caller-persisted bytes but does not by itself prove provider authorship or correctness.

Each explicit phase permits at most one fixed mini54 low/4000/30s request under its own durable attempt/raw journal and ordinary ledger. Actual full-body/image bounds apply before reservation. Current source changes fail before/after the request; model/schema/usage failures retain original raw. No phase automatically calls another phase, repeats a request, searches missing evidence or upgrades a model. The new phases have no live-model accuracy acceptance yet.

Every new result remains `semanticVerified=false`; local `localReady` is a fallible diagnostic only. `wholeAnswerVerified=false`, `fullSourceCoverage=unassessed` and `conflictExhaustiveness=unassessed` remain explicit. Contract interpretation and source-derived sub-scopes can both be wrong. A local pass cannot certify an entire source, a complete list, all conflicts or the usefulness/completeness of the final multi-source answer. Historical optional-count errors and scores are not regraded by changing the contract.

## Short answer chain

`KernelService.answerPlannedStudyContent(owner, query, savedContract, {courseId?}, policy)` is an explicit development chain. It reuses the saved real question contract, sends one contract-bound plan, performs one batch of at most two lexical supplemental queries, sends one final generation, and audits only the actual final claims using the existing physically isolated citation-local checker. It does not call the cluster pre-check, replan, revise citations, regenerate answers or upgrade models.

Only this short-chain entry also accepts an explicit `sourceHint: {selectedDocumentTitle}`. The complete title must appear in the original question under NFKC normalization and uniquely resolve against the current entire owner/course-visible corpus using the existing exact-title resolver. Initial14 retrieval stays global; only the two supplemental queries use the selected title, without altering their relevance query or relying on its40-token lexical limit. Ambiguous, missing or changed sources fail explicitly. The receipt records global initial retrieval, supplemental selected-title scope, the user title and current resolved version/hash. No hint is inferred from a plan, top hit or expected document. Without a hint supplements remain global, including multi-source questions; selecting one title cannot claim coverage of all other sources. This is explicit user-source resolution, not improved unknown-source global recall.

Missing-evidence lexical queries have priority. Remaining query slots use natural aspect/scope words from the question contract, even when the fallible planner asserts sufficient. This improves candidate recall without certifying relevance. Every query, origin requirement, actual ranking/source identity and selection is retained in the composite receipt. There are no Gold document filters. The initial14 anchors remain protected; each supplemental reader uses at most4, preserving the ordinary per-reader14 limit. The new composite protocol therefore permits at most22 original ranked anchors and does not alter default answering or the historical planning protocol.

Original evidence and source-stable q IDs are retained. Re-retrieving an existing page also exposes its previously unselected quote units. Original image order/IDs have priority under the same global64-image/32MiB/65536-image-token budget. Prior reader omissions and new global omissions remain recorded. The original query's image-only native-table lane stays bounded to two anchors; supplemental readers disable that extra lane, while their verified caption/PDF-page images remain eligible. This is a declared table-recall limitation. Current source/evidence, parent manifests and original selections are revalidated throughout; no stale-source error is swallowed.

Generation sees the complete original question plus contract aspects/scope, the explicitly unverified advisory plan, all original selectable quote units and already budgeted original images, and actual supplemental candidates. The plan cannot discard already retrieved original text or images. Original image order and the shared image budget stay fixed; this adds no new image retrieval. The actual complete generation body still undergoes the existing input/enum/image/funding bounds; overflow fails without truncation. Source plans and `sufficient` statuses never establish facts. Only the final claims' restored actual citations enter local checking; outside text/images cannot rescue them. More than six claims retains the untruncated raw result as `capacity-exceeded` and runs no claim audit. A neutral refusal remains a refusal; it cannot pass an answerable test. Local failures retain the answer and unresolved claim indices rather than silently deleting or repairing claims. Previous planning gaps are retained as unassessed, and final usefulness/completeness still require independent whole-question grading.

Per question the exact maximum is **one plan + one generation + K local audits,0≤K≤6**: at most8 model requests (48 for six questions), plus at most two lexical searches with no embedding/rerank request. Plan/generation remain mini54 low/4000/30s; final local checks remain mini54 low/1000/30s. Every actual phase body, image bound, ordinary reservation and usage upper is journaled before its request, with raw before parsing and no retry. The mathematical context/reservation extreme is US$2.463 per question (US$14.778 for six); it is not a pilot budget or authorization. The controlled six-question pilot must enforce its separately approved tighter total cap and stop on pending, unknown, overflow, invalid output or source changes. No follow-on paid chain has been executed as part of this code change.
