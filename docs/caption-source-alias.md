# Request-local caption image aliases (Issue175)

The development planned-answer policy optionally accepts `sourceLabelPolicy: 'caption-alias-v2'`, only on the verified complete single-source route. Omission retains the original v1 mapping, receipt fields, body and identities, including historical v7/v8/v9 and old complete-source-v1 requests. No default setting, UI or production route changes.

The eighth optional argument of `preparePlannedStudyGeneration(question, context, extras, contract, binding, queries, selectedSource, sourceLabelPolicy)` records this policy only when explicitly selected. The integrated caller and Kernel's actual generation-capacity precheck pass it through. `preparePlannedStudyGenerationTransport` dispatches from the receipt's own policy, never from a later run's preference. The new mapping/binding version is `request-local-caption-alias-v2`; the policy, actual mapping and body all enter their existing hashes.

Only one already-paired author-caption visual unit, beginning at actual caption offset0 and anchored to a genuine caption node in the complete manifest, is eligible. The first64 UTF16 units may contain a bounded leading `Table`, `Figure` or `Fig.` label with a 1–4 digit number and colon or period delimiter. Compound numbers, other languages, unknown/no paired caption, PDF page images and conflicting duplicate numbers fall back to their original request-local `SourceN`. Duplicate comparisons normalize only numeric leading zeros and Figure/Fig. spellings. No question, answer, filename, model or expected table ID supplies an alias.

For example `Table1_Image4` refers to printed caption Table1 on the fourth actual supplied image, whose canonical ID remains `i3`. Images are never sorted by table number. All original q/i selections, caption text/offsets, source identities, image bytes and order remain unchanged. The same mapping produces image metadata IDs, adjacent caption/image labels, schema enums and strict response decoding. Text selections retain their original `SourceN`. A caption-derived alias is navigation metadata, never proof of numerical or semantic support.

Full-source diagnostics and the separately versioned content proposal use their actual original transport mapping. A new alias answer may therefore be reviewed/revised, while original selected-only audits keep their own canonical binding and physically selected rN packet. An old v1 response cannot be relabeled as an alias response: transport, request/raw identity and source rechecks must match. A historical independent reader must rebuild its packet with **that artifact's** `receipt.sourceLabelPolicy` (usually undefined), not the current experiment's policy. Explicitly changing an original artifact's policy is rejected. Old raw, failures, ledger rows and scores stay historical.

Actual longer aliases pass through existing schema enum/string limits and full request/image/funding bounds; no limit increases or silent evidence truncation are added. Three new focused scenarios cover conservative aliases/fallbacks and actual schema budget, default/historical behavior and pre-request rejection, and integrated generation→full-source review→one content proposal with fresh selected-only audit. They use synthetic source/PNG and mocked HTTP, no real API/PG/PDF operation. These checks do not show that aliases reduce model citation errors; a coordinator-controlled single exposed-question pilot and independent source review are still required.
